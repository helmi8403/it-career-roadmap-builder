05 | Data platforms, storage and analytics

Official Azure reference diagrams·Study guide prepared October 2026

Exam mapping: Data storage (20–25%)

Data questions often hinge on service limits, consistency, migration compatibility, cross-database queries, scalability and business recovery needs. Identify the data model and access path before comparing products.

Azure SQL options

Azure SQL Database is a highly managed relational PaaS; elastic pools share reserved resources across variable databases; Hyperscale supports very large databases; SQL Managed Instance provides stronger instance-level SQL compatibility; SQL Server on VMs offers maximal legacy control.

Availability tiers

General Purpose prioritizes value and remote storage; Business Critical uses local SSD and high availability architectures; Hyperscale is optimized for large database scale and different storage architecture. Always read the precise service-tier feature limitations and latest regional support.

NoSQL models

Cosmos DB offers globally distributed NoSQL APIs with consistency and throughput choices; choose data partitions carefully to avoid hot partitions and runaway request-unit charges. PostgreSQL distributed service naming has changed as products retire.

Unstructured storage

Blob Storage handles object data; Azure Files exposes SMB/NFS shares; ADLS Gen2 with hierarchical namespace supports analytics file-system operations; managed disks serve VM block storage. Durability (LRS/ZRS/GRS/GZRS) and availability/RA read access differ.

Analytics stack

Data Factory orchestrates ingestion and transformation; Synapse/Fabric offer data warehousing and analytics capabilities; Databricks is suited to Spark and advanced data engineering. Services overlap, so check integration, masking, autoscaling and operational requirements.

Data protection

Classify accidental deletion vs ransomware vs regional outage separately. Soft delete, versioning, immutable blobs, point-in-time restore, backups and asynchronous object replication serve different recovery threats.

Service-choice matrix

Requirement Evaluate first Why
Many small, intermittent SQL databases Elastic pool Share provisioned compute / cost
Very large individual Azure SQL databases Hyperscale Storage scales beyond conventional tiers
Instance features and cross-database references SQL Managed Instance Higher SQL Server compatibility
Unsupported SQL features / custom OS agents SQL Server on VM Maximum control, maximum ops
File analytics and ACL-aware directory paths ADLS Gen2 HNS Hierarchical namespace
Durable shared SMB drive Azure Files + identity Share protocol, backup and sync needs
Operational NoSQL globally distributed Cosmos DB Partition key, RU and consistency tradeoffs

Exam traps and design warnings

  • ZRS is within a region; GRS protects data to a second region but does not automatically make the secondary read-writable.

  • A migration assessment score does not replace requirement-by-requirement compatibility validation.

  • Redis and Cosmos DB for PostgreSQL retirement paths must be checked against 2026 documentation.

Guided lab: Database and data-lake migration decision record

  1. Compare a 600 GB transactional database, a 15 TB growth scenario, a 500 TB archive and distributed PostgreSQL transactions.

  2. Write a target selection matrix: SQL Database, Managed Instance, VM, Cosmos DB, Data Lake/Fabric.

  3. Design data migration with cutover, test migration, rollback and validation steps; separate offline transfer from network migration.

  4. Build an immutable-blob protection design and explain its retention/lock implications.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.
