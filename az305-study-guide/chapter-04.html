04 | Compute, containers and application integration

Official Azure reference diagrams·Study guide prepared October 2026

Exam mapping: Infrastructure (30–35%)

Pick the least operationally intensive platform that meets runtime constraints. Start with the workload: legacy OS, protocol, tenancy, cold-start tolerance, GPU/HPC, container control, portability and deployment frequency.

Compute continuum

VMs give deep OS control but higher patching burden; App Service handles common web workloads; Functions run event-driven functions; Container Apps support managed container scaling; AKS provides extensive Kubernetes control at additional operational cost.

Availability and scaling

Availability zones protect against a zone failure, not a region failure. VMSS can scale VM fleets, AKS manages pods and node pools, App Service scales app instances, and Functions/Container Apps have distinct trigger/replica mechanisms.

Messaging versus events

Service Bus is a durable enterprise message broker with queues, topics and sessions; Event Grid distributes discrete events to subscribers; Event Hubs ingests high-volume event streams; Storage Queues are lightweight task queues.

Patterns

Use queue-based load leveling to smooth peaks, publish-subscribe for fan-out, dead-letter queues to isolate poison messages, idempotency to tolerate retries, and outbox/Saga patterns for distributed business processes.

Application configuration and caching

Azure App Configuration centralizes feature flags; Key Vault protects secrets; Azure Managed Redis can provide low-latency caches. TTL, invalidation and data staleness must be part of the design.

API security

API Management centralizes policy, throttling and API lifecycle; do not mistake it for a load balancer. Private networking, OAuth validation and backend identities need separate design.

Service-choice matrix

Scenario Best starting point When not to choose
Traditional managed web API App Service Not a good fit for non-HTTP custom kernel dependencies
Short event-driven code Azure Functions Long-running fixed-capacity service may favor another platform
Container with HTTP / event scaling Azure Container Apps Do not assume full Kubernetes control
Advanced Kubernetes policies/operators AKS Operational overhead is justified only when needed
Ordered enterprise business transactions Service Bus sessions Not high-throughput telemetry firehose
Mass IoT or clickstream intake Event Hubs Not business queue semantics
Blob-created trigger to webhook Event Grid Not durable large command queue

Exam traps and design warnings

  • FIFO ordering must be considered per Service Bus session, with appropriate client design.

  • Event-driven does not automatically mean at-most-once processing; design idempotency.

  • “Minimize administration” is a strong reason not to default to AKS or VMs.

Guided lab: Asynchronous order-processing architecture

  1. Draw Front Door → App Service/Container Apps → Service Bus queue → Functions → managed SQL with retries, dead-lettering and telemetry.

  2. State ordering guarantees and design an idempotency key for duplicate messages.

  3. Design Dev/Test/Prod promotion using Bicep or Terraform and managed identities.

  4. Estimate high-level monthly cost drivers and explain why scaling alone does not remove the need for backpressure.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.
