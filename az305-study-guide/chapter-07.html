Chapter 7 · AZ-305

07 | Migration, landing zones and the architecture case study

Official Azure reference diagrams·Study guide prepared October 2026

Exam mapping: Infrastructure (30–35%), integration with all domains

Enterprise migration begins with discovery and business outcomes. Map the applications, dependencies, costs and governance requirements first; do not simply replicate VMs into cloud and call it an architecture.

Landing-zone architecture

Separate platform services, connectivity, management and identity from application landing zones. Use policy, RBAC and IaC to enforce standards consistently.

Migration strategy

Evaluate rehost, replatform, refactor and retire/retain based on effort, risk, compatibility, service-life and business benefits. Assess before selecting; test before cutover.

Migration tools

Azure Migrate discovers, assesses and supports server migrations; Database Migration Service and SQL migration tooling depend on source/target and supported modes; Data Box supports physical offline transfers where bandwidth constraints dominate.

Enterprise integrations

Treat identity, DNS, network connectivity, service endpoints and data quality as first-class migration dependencies. Write rollback and cutover checklists.

Infrastructure as code

Bicep, ARM and Terraform support repeatable deployments. Design secretless pipeline identity, module versioning, policy testing and drift monitoring.

Architectural decision records

Keep a short ADR for each major tradeoff: context, constraints, options, decision, risk, mitigations, validation evidence and rollback. Explain “why not” the alternative.

Service-choice matrix

Workload Likely pattern Critical assessment
Legacy supported VM workload Azure Migrate → Azure VM Dependencies, drivers, unsupported components
SQL requiring managed operations DMS/SQL migration → MI/SQL DB Feature parity, downtime and cutover
Very large offline initial transfer Azure Data Box Handling and data-reconciliation processes
Enterprise foundation across many subscriptions Azure landing zone IaC accelerator Bicep/Terraform and platform ownership

Exam traps and design warnings

  • An app can be technically migrated but still fail compliance due to data residency and access design.

  • Migrate the identity, DNS and networking dependencies, not just a machine image.

  • The least costly option at launch can be expensive over three years if operations and rework dominate.

Guided exercise: Enterprise migration architecture review

  1. Define a realistic enterprise migration scenario including applications, data stores, identity and connectivity.

  2. Draw the current-state and target-state architectures. Identify network, identity, SQL, storage, resilience and cost requirements.

  3. Write architecture decision records for data protection, database service tiers, private networking and governance.

  4. Model zone and region failures, documenting recovery objectives and what the Azure SLA does and does not guarantee.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.
