06 | Resilience, backup and disaster recovery

Official Azure reference diagrams·Study guide prepared October 2026

Exam mapping: Business continuity (15–20%)

Treat availability, durability and recoverability as three different objectives. A replica can improve uptime yet spread logical corruption; a backup can restore corruption but may miss the RPO; a DR plan can fail because nobody tested dependencies.

Define RTO, RPO and SLA

Recovery Time Objective is maximum tolerable restoration time. Recovery Point Objective is maximum acceptable data loss. A platform SLA is a vendor commitment under specified configuration assumptions and cannot alone prove business-level recovery.

Failure domains

Availability sets reduce host fault risk; Availability Zones reduce zonal risk; paired/multi-region strategies address regional disasters. A design must identify how traffic, state, identity, certificates and DNS recover.

Backup versus replication

Azure Backup provides recoverable versions; Azure Site Recovery orchestrates VM DR replication/failover; storage geo-replication protects copies but is not an immutable point-in-time backup; database failover groups support designed SQL continuity.

Cross-tenant ransomware protection

Separate authorization for destructive backup operations using supported Resource Guard / multi-user authorization models; combine soft delete, immutability, alerts, credential isolation and restore testing.

Consistency and limitations

Crash-consistent and application-consistent restores have different guarantees. Shared-disk and special workload support must be validated; do not assume a blanket “VM backup” capability applies to every disk configuration.

Chaos and DR tabletop

Validate real operational failover, not just resource deployment. Document preconditions, a communication tree, switchback steps and clean environment teardown.

Service-choice matrix

Need Candidate design Design note
Protect against app/data corruption Backups + versioning/PITR Replication alone cannot undo corruption
VM recovery in another region Azure Site Recovery Test failover and failback
Zone fault tolerance for stateless app Multi-zone compute + load balancing State tier also requires HA
Near-zero region outage for relational tier Cross-region failover group Test writes, lag and data loss behavior
Guard deletion of backups Resource Guard, multi-user authorization Independent control/tenant model

Exam traps and design warnings

  • Two simultaneous availability-zone losses are not automatically covered by every zonal configuration.

  • “Monthly full backup” is not equivalent to a DR strategy without RPO/RTO targets.

  • Backup retention and geo-replication limits change by SKU and service.

Guided lab: Business continuity tabletop

  1. Define workload SLO 99.9%, target RTO 2 hours and RPO 15 minutes; explain what budget/design this implies.

  2. Build a dependency map for app, identity, key storage, SQL, messaging and DNS.

  3. Simulate single VM, zone, region and ransomware failures; describe response sequence for each.

  4. Explain why a high-availability database tier does not automatically guarantee tolerance of two simultaneous availability-zone failures.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.
