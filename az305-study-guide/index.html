Personal study cadence and assumptions

This plan assumes eight weeks from Monday 26 October through Sunday 20 December 2026, approximately 10 hours per week: 75 minutes Monday–Friday, 150 minutes Saturday and 90 minutes Sunday. The dates are suggestions, not an exam booking. For an experienced cloud engineer, spend less time on basic provisioning and more time explaining system-level tradeoffs, risk, availability, pricing and governance.

Daily 75-minute session: 15 minutes recall → 30 minutes official docs + comparative notes → 20 minutes scenario practice → 10 minutes error log. Weekend lab: 30 minutes design + 80 minutes implementation/whiteboard + 30 minutes evidence/ADR + 10 minutes teardown plan. Do not incur Azure charges without setting an appropriate subscription budget and deleting resources afterwards.

Architect decision workflow

Diagrams in this study guide are original Microsoft Azure / Microsoft Learn reference diagrams, not diagrams of a deployed tenant. Use the source links under each diagram for the current assumptions and constraints. An internet connection is needed to display official diagrams.

  1. Restate business outcomes (availability, security, budget, data residency, governance).
  2. Identify must-haves versus preferences and quantify RTO/RPO/latency/retention.
  3. Map actors, tenants, subscriptions, regions, networks, data flow and failure domains.
  4. Shortlist two or three supported architectures and compare feature, scale, cost and administrative effort.
  5. Reject any design violating a must-have.
  6. Decide the minimal supported design, with documented assumptions.
  7. Validate SKU limits, retirement state, test plan, rollback and observability.

Comprehensive curriculum

01 | Architect mindset, governance and identity

Exam mapping: Identity, governance and monitoring (25–30%)

AZ-305 tests your ability to recommend a defensible design under constraints. Begin with users, network boundaries, organizational ownership, risk appetite, regulatory needs and cost. Do not assume that the technically richest SKU is the best. State the simplest design that meets every explicit requirement, then check its limitations.

Requirements to decisions

Translate words such as minimize operations, private access, automatic deletion, least privilege, cross-tenant, automatic recovery and no downtime into capabilities you can test. Make a short requirements matrix before choosing a service. Mark mutually conflicting requirements.

Management hierarchy

Management groups organize policy inheritance across subscriptions. Subscriptions are boundaries for billing, quota and governance; resource groups are deployment and lifecycle containers. Use resource tags for ownership and cost classification, not as a security boundary.

Authorization vs authentication

Microsoft Entra ID establishes identity and supports authentication; Azure RBAC controls authorization to Azure control-plane resources. Data-plane access can use service-specific RBAC and access policies. An Entra directory role is not interchangeable with an Azure resource role.

Identity lifecycle and privileges

Access reviews periodically re-evaluate entitlement; entitlement management packages resources and approval workflows; PIM provides just-in-time privileged access; lifecycle workflows automate joiner/mover/leaver. Select the capability matching the verb in the question.

Conditional access

Conditional Access combines assignment criteria (users, cloud apps, network locations, devices, sign-in risk) with grants (MFA, compliant device, block). Risk-based policies are not direct substitutes for network-location conditions.

Secrets and key management

Managed identities remove application credential maintenance when supported; workload identity federation reduces static secrets in CI/CD; Key Vault controls secrets, keys and certificates, with network restrictions and monitored data-plane access.

Service-choice matrix

Requirement Default shortlist Discriminator
MFA only from untrusted locations Conditional Access Use a network/location condition, not sign-in-risk alone
Time-limited elevation PIM Activations, approval, just-in-time role assignment
Recurring membership validation Access reviews Automatic removal of denied / nonresponders
Cross-tenant external onboarding Entitlement management Connected organizations, access packages
Deploy Azure governance at scale Management groups + Azure Policy Inheritance, scope, exemptions, remediation
Application authentication without passwords Managed identity / federation Which runtime and trust boundary?

Exam traps and design warnings

  • Azure Policy can audit or enforce resource configuration; it does not grant Azure RBAC permissions to users.

  • A Modify or DeployIfNotExists remediation task requires appropriate managed identity permissions.

  • Use Privileged Identity Management for elevation, not for ordinary quarterly membership attestation.

Guided lab: Governed platform blueprint

  1. Draw a tenant with root, platform, landing-zone and sandbox management groups. Document policy inheritance and exceptions.

  2. Implement a sandbox policy initiative with required tags and location controls. Inspect compliance, then create an exemption.

  3. Create a test group and an access-review design; explain how decisions and nonresponse are handled.

  4. Write an ADR: why you chose Conditional Access over Identity Protection for a network-location MFA rule.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

  • Q3: Design the quarterly access review including nonresponse handling.

02 | Observability, logging and security operations

Exam mapping: Identity, governance and monitoring (25–30%)

Architect monitoring by starting with the signal and the response: metrics and resource health for platform behavior, resource logs for detailed operations, application telemetry for user experience and dependencies, and security products for threat findings.

Data types

Azure Activity Log captures subscription control-plane events; resource logs capture service-specific operations through diagnostic settings; Azure Monitor metrics capture numeric time-series values; Log Analytics stores searchable logs; Application Insights provides application performance and user telemetry.

Routing and retention

Send diagnostic logs to Log Analytics for KQL investigations, Event Hubs for downstream SIEM integration or Storage for long-term archive. Match retention, ingestion volume, latency and compliance needs.

Alerts and response

Metric alerts suit thresholded telemetry and can be low latency. Log alerts support complex KQL. Action groups route notifications and trigger automation. Service Health is distinct from Resource Health.

Private monitoring

Azure Monitor Private Link Scope can restrict telemetry ingestion/query paths where supported; confirm DNS, network egress and managed endpoint service compatibility.

Observability SLOs

Define measurable SLI/SLO indicators: request success rate, latency percentiles, dependency failure rate, data freshness and recovery health. Alert on user-impacting symptoms before infrastructure noise.

Service-choice matrix

Need Service / feature Decision reason
Monthly report of deployment events Activity Log + export/query Control-plane deployment events
External SIEM pipeline Diagnostic settings → Event Hubs Stream platform/resource logs to consumer
Web UX, availability and dependency tracing Application Insights Application-layer instrumentation
Cheap long-term audit archive Storage account via diagnostic settings Retention and immutable storage when required
Advanced KQL cross-resource detection Log Analytics workspace Schema and retention cost design

Exam traps and design warnings

  • Activity Log is not a replacement for all data-plane auditing.

  • Metrics and logs have different cost/retention/query characteristics.

  • Never infer that enabling diagnostic settings automatically configures security alert rules.

Guided lab: End-to-end telemetry pipeline

  1. Create a minimal test resource and Log Analytics workspace with a bounded budget.

  2. Route a supported diagnostic category to Log Analytics; run a KQL query that filters by OperationName or ResourceId.

  3. Define a metric alert with an action group and a simple runbook response outline.

  4. Draft a retention matrix: 30-day operational search, 1-year audit access, 5-year archive. Explain costs and controls.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

Tie-in to your question bank

  • Q10: distinguish Activity Log from Azure Monitor metrics.

  • Q21: choose telemetry that reveals end-user behavior.

  • Q27/Q37/Q50: design log routing and data-plane Key Vault auditing.

03 | Networking and connectivity architecture

Exam mapping: Infrastructure (30–35%)

Treat networking as a traffic-path design exercise. Sketch source, destination, protocol, port, DNS resolution, routes, firewalls, TLS boundaries and name resolution before picking a service.

Network topology

Hub-spoke centralizes shared connectivity and governance; Azure Virtual WAN provides a managed transit architecture for larger multi-region environments. VNet peering is not automatically transitive; route tables and gateway transit matter.

Hybrid connectivity

VPN Gateway offers encrypted internet tunnels; ExpressRoute is private dedicated connectivity but requires network redundancy and encryption choices; Virtual WAN connects branches and regions with managed hubs.

Private service endpoints

Private Endpoints place a private IP for a specific PaaS service into a VNet. Private DNS zones and resolver/forwarding paths are essential, especially for on-premises clients. Service Endpoints use a different security model and do not create a private endpoint NIC.

Traffic distribution

Azure Load Balancer operates at Layer 4; Application Gateway handles Layer 7 regional web routing and WAF; Front Door provides global entry, acceleration and layer-7 routing; Traffic Manager is DNS-based, not an inline packet proxy.

Network security

Use NSGs for subnet/NIC traffic controls; Azure Firewall or NVA for centralized stateful filtering; DDoS Protection for volumetric protection; Bastion for safer VM management access.

DNS is a dependency

When Private Link “does not work,” first verify records, split-horizon DNS, resolver paths and expected target IPs before changing firewall rules.

Service-choice matrix

Question wording Prefer evaluating Watch out
Private web load balancing in one VNet Internal Application Gateway Layer 7 only if HTTP(S)
TCP or UDP regional load balancing Azure Load Balancer Not WAF / app-layer routing
Global public HTTP failover and WAF Azure Front Door Regional requirements may still need back-end balancing
Global DNS routing Traffic Manager DNS caching and no direct proxy
Many branches and hubs Azure Virtual WAN Check routing intent and regional coverage
Private PaaS data access Private Endpoint + DNS Public network access disablement is separate

Exam traps and design warnings

  • Always note regional vs global and Layer 4 vs Layer 7.

  • An NSG does not provide a native stateful centralized application FQDN policy equivalent to Azure Firewall.

  • SMB over QUIC uses UDP 443; a question requiring TCP 445 is materially different.

Guided lab: Hub and spoke design exercise

  1. Draw a hub VNet, two application spokes, a firewall, Bastion, private DNS resolver and ExpressRoute/VPN gateway.

  2. Trace five flows including on-premises → Key Vault private endpoint and spoke A → spoke B.

  3. Sketch DNS records for a private storage account endpoint and explain how on-premises resolves them.

  4. Create a table comparing L4 load balancer, regional L7 gateway, global L7 Front Door and DNS Traffic Manager.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

Tie-in to your question bank

  • Q6: why a private Application Gateway can satisfy regional HTTP load balancing.

  • Q8: explain protocol conflict between TCP 445 and SMB over QUIC.

  • Q19/Q33/Q38: compare Virtual WAN and DNS Private Resolver.

04 | Compute, containers and application integration

Exam mapping: Infrastructure (30–35%)

Pick the least operationally intensive platform that meets runtime constraints. Start with the workload: legacy OS, protocol, tenancy, cold-start tolerance, GPU/HPC, container control, portability and deployment frequency.

Compute continuum

VMs give deep OS control but higher patching burden; App Service handles common web workloads; Functions run event-driven functions; Container Apps support managed container scaling; AKS provides extensive Kubernetes control at additional operational cost.

Availability and scaling

Availability zones protect against a zone failure, not a region failure. VMSS can scale VM fleets, AKS manages pods and node pools, App Service scales app instances, and Functions/Container Apps have distinct trigger/replica mechanisms.

Messaging versus events

Service Bus is a durable enterprise message broker with queues, topics and sessions; Event Grid distributes discrete events to subscribers; Event Hubs ingests high-volume event streams; Storage Queues are lightweight task queues.

Patterns

Use queue-based load leveling to smooth peaks, publish-subscribe for fan-out, dead-letter queues to isolate poison messages, idempotency to tolerate retries, and outbox/Saga patterns for distributed business processes.

Application configuration and caching

Azure App Configuration centralizes feature flags; Key Vault protects secrets; Azure Managed Redis can provide low-latency caches. TTL, invalidation and data staleness must be part of the design.

API security

API Management centralizes policy, throttling and API lifecycle; do not mistake it for a load balancer. Private networking, OAuth validation and backend identities need separate design.

Service-choice matrix

Scenario Best starting point When not to choose
Traditional managed web API App Service Not a good fit for non-HTTP custom kernel dependencies
Short event-driven code Azure Functions Long-running fixed-capacity service may favor another platform
Container with HTTP / event scaling Azure Container Apps Do not assume full Kubernetes control
Advanced Kubernetes policies/operators AKS Operational overhead is justified only when needed
Ordered enterprise business transactions Service Bus sessions Not high-throughput telemetry firehose
Mass IoT or clickstream intake Event Hubs Not business queue semantics
Blob-created trigger to webhook Event Grid Not durable large command queue

Exam traps and design warnings

  • FIFO ordering must be considered per Service Bus session, with appropriate client design.

  • Event-driven does not automatically mean at-most-once processing; design idempotency.

  • “Minimize administration” is a strong reason not to default to AKS or VMs.

Guided lab: Asynchronous order-processing architecture

  1. Draw Front Door → App Service/Container Apps → Service Bus queue → Functions → managed SQL with retries, dead-lettering and telemetry.

  2. State ordering guarantees and design an idempotency key for duplicate messages.

  3. Design Dev/Test/Prod promotion using Bicep or Terraform and managed identities.

  4. Estimate high-level monthly cost drivers and explain why scaling alone does not remove the need for backpressure.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

  • Q5: ACR base-image update automation.

  • Q7: feature flags vs secrets.

  • Q17: durable FIFO messaging and storage-created events.

05 | Data platforms, storage and analytics

Exam mapping: Data storage (20–25%)

Data questions often hinge on service limits, consistency, migration compatibility, cross-database queries, scalability and business recovery needs. Identify the data model and access path before comparing products.

Azure SQL options

Azure SQL Database is a highly managed relational PaaS; elastic pools share reserved resources across variable databases; Hyperscale supports very large databases; SQL Managed Instance provides stronger instance-level SQL compatibility; SQL Server on VMs offers maximal legacy control.

Availability tiers

General Purpose prioritizes value and remote storage; Business Critical uses local SSD and high availability architectures; Hyperscale is optimized for large database scale and different storage architecture. Always read the precise service-tier feature limitations and latest regional support.

NoSQL models

Cosmos DB offers globally distributed NoSQL APIs with consistency and throughput choices; choose data partitions carefully to avoid hot partitions and runaway request-unit charges. PostgreSQL distributed service naming has changed as products retire.

Unstructured storage

Blob Storage handles object data; Azure Files exposes SMB/NFS shares; ADLS Gen2 with hierarchical namespace supports analytics file-system operations; managed disks serve VM block storage. Durability (LRS/ZRS/GRS/GZRS) and availability/RA read access differ.

Analytics stack

Data Factory orchestrates ingestion and transformation; Synapse/Fabric offer data warehousing and analytics capabilities; Databricks is suited to Spark and advanced data engineering. Services overlap, so check integration, masking, autoscaling and operational requirements.

Data protection

Classify accidental deletion vs ransomware vs regional outage separately. Soft delete, versioning, immutable blobs, point-in-time restore, backups and asynchronous object replication serve different recovery threats.

Service-choice matrix

Requirement Evaluate first Why
Many small, intermittent SQL databases Elastic pool Share provisioned compute / cost
Very large individual Azure SQL databases Hyperscale Storage scales beyond conventional tiers
Instance features and cross-database references SQL Managed Instance Higher SQL Server compatibility
Unsupported SQL features / custom OS agents SQL Server on VM Maximum control, maximum ops
File analytics and ACL-aware directory paths ADLS Gen2 HNS Hierarchical namespace
Durable shared SMB drive Azure Files + identity Share protocol, backup and sync needs
Operational NoSQL globally distributed Cosmos DB Partition key, RU and consistency tradeoffs

Exam traps and design warnings

  • ZRS is within a region; GRS protects data to a second region but does not automatically make the secondary read-writable.

  • A migration assessment score does not replace requirement-by-requirement compatibility validation.

  • Redis and Cosmos DB for PostgreSQL retirement paths must be checked against 2026 documentation.

Guided lab: Database and data-lake migration decision record

  1. Compare a 600 GB transactional database, a 15 TB growth scenario, a 500 TB archive and distributed PostgreSQL transactions.

  2. Write a target selection matrix: SQL Database, Managed Instance, VM, Cosmos DB, Data Lake/Fabric.

  3. Design data migration with cutover, test migration, rollback and validation steps; separate offline transfer from network migration.

  4. Build an immutable-blob protection design and explain its retention/lock implications.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

06 | Resilience, backup and disaster recovery

Exam mapping: Business continuity (15–20%)

Treat availability, durability and recoverability as three different objectives. A replica can improve uptime yet spread logical corruption; a backup can restore corruption but may miss the RPO; a DR plan can fail because nobody tested dependencies.

Define RTO, RPO and SLA

Recovery Time Objective is maximum tolerable restoration time. Recovery Point Objective is maximum acceptable data loss. A platform SLA is a vendor commitment under specified configuration assumptions and cannot alone prove business-level recovery.

Failure domains

Availability sets reduce host fault risk; Availability Zones reduce zonal risk; paired/multi-region strategies address regional disasters. A design must identify how traffic, state, identity, certificates and DNS recover.

Backup versus replication

Azure Backup provides recoverable versions; Azure Site Recovery orchestrates VM DR replication/failover; storage geo-replication protects copies but is not an immutable point-in-time backup; database failover groups support designed SQL continuity.

Cross-tenant ransomware protection

Separate authorization for destructive backup operations using supported Resource Guard / multi-user authorization models; combine soft delete, immutability, alerts, credential isolation and restore testing.

Consistency and limitations

Crash-consistent and application-consistent restores have different guarantees. Shared-disk and special workload support must be validated; do not assume a blanket “VM backup” capability applies to every disk configuration.

Chaos and DR tabletop

Validate real operational failover, not just resource deployment. Document preconditions, a communication tree, switchback steps and clean environment teardown.

Service-choice matrix

Need Candidate design Design note
Protect against app/data corruption Backups + versioning/PITR Replication alone cannot undo corruption
VM recovery in another region Azure Site Recovery Test failover and failback
Zone fault tolerance for stateless app Multi-zone compute + load balancing State tier also requires HA
Near-zero region outage for relational tier Cross-region failover group Test writes, lag and data loss behavior
Guard deletion of backups Resource Guard, multi-user authorization Independent control/tenant model

Exam traps and design warnings

  • Two simultaneous availability-zone losses are not automatically covered by every zonal configuration.

  • “Monthly full backup” is not equivalent to a DR strategy without RPO/RTO targets.

  • Backup retention and geo-replication limits change by SKU and service.

Guided lab: Business continuity tabletop

  1. Define workload SLO 99.9%, target RTO 2 hours and RPO 15 minutes; explain what budget/design this implies.

  2. Build a dependency map for app, identity, key storage, SQL, messaging and DNS.

  3. Simulate single VM, zone, region and ransomware failures; describe response sequence for each.

  4. For Litware SQL Q2/Q4, write a note explaining why the proposed Business Critical service does not make all two-zone outage assumptions valid.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

07 | Migration, landing zones and the architecture case study

Exam mapping: Infrastructure (30–35%), integration with all domains

Enterprise migration begins with discovery and business outcomes. Map the applications, dependencies, costs and governance requirements first; do not simply replicate VMs into cloud and call it an architecture.

Landing-zone architecture

Separate platform services, connectivity, management and identity from application landing zones. Use policy, RBAC and IaC to enforce standards consistently.

Migration strategy

Evaluate rehost, replatform, refactor and retire/retain based on effort, risk, compatibility, service-life and business benefits. Assess before selecting; test before cutover.

Migration tools

Azure Migrate discovers, assesses and supports server migrations; Database Migration Service and SQL migration tooling depend on source/target and supported modes; Data Box supports physical offline transfers where bandwidth constraints dominate.

Enterprise integrations

Treat identity, DNS, network connectivity, service endpoints and data quality as first-class migration dependencies. Write rollback and cutover checklists.

Infrastructure as code

Bicep, ARM and Terraform support repeatable deployments. Design secretless pipeline identity, module versioning, policy testing and drift monitoring.

Architectural decision records

Keep a short ADR for each major tradeoff: context, constraints, options, decision, risk, mitigations, validation evidence and rollback. Explain “why not” the alternative.

Service-choice matrix

Workload Likely pattern Critical assessment
Legacy supported VM workload Azure Migrate → Azure VM Dependencies, drivers, unsupported components
SQL requiring managed operations DMS/SQL migration → MI/SQL DB Feature parity, downtime and cutover
Very large offline initial transfer Azure Data Box Handling and data-reconciliation processes
Enterprise foundation across many subscriptions Azure landing zone IaC accelerator Bicep/Terraform and platform ownership

Exam traps and design warnings

  • An app can be technically migrated but still fail compliance due to data residency and access design.

  • Migrate the identity, DNS and networking dependencies, not just a machine image.

  • The least costly option at launch can be expensive over three years if operations and rework dominate.

  3. Write ADRs for storage immutability, SQL tier, private endpoints and centralized governance; quantify risk assumptions.

  4. Challenge the source bank’s zone outage claim and propose an architecture that actually meets the stated failure tolerance.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

08 | Synthesis, exam technique and readiness

Exam mapping: All four domains

The final stretch is active retrieval, not binge watching. For each scenario, identify the controlling requirement, eliminate three wrong designs, and explain why the surviving design works. Then validate the answer with a current primary document.

Case-study technique

Read high-level business goals once; extract numeric constraints, subscriptions, tenants, regions and critical requirements into a scratch matrix; only then answer each question.

Hotspot technique

Treat each row independently. A single incorrect dropdown makes a multi-part answer unreliable; pay attention to source screenshots and supported combinations.

Elimination technique

Use a consistent sequence: wrong scope, wrong network layer, unsupported feature, wrong availability/consistency, excessive ops/cost. Do not select a service just because it appears often in bank answers.

Time strategy

Practice with an exam-style timer and review remaining items periodically; do not assume a precise question count from third-party sites. Use the official Microsoft exam sandbox to learn navigation.

Readiness measurements

Track fresh-question scores by domain; calculate first-attempt accuracy separately from repeated-study recall. Record critical architecture-conflict questions as unresolved until checked.

Error log

For each miss, write the tested requirement, why your selected option fails, exact disambiguating fact and link to evidence. Convert only validated distinctions into flashcards.

Checkpoint Target Rule

Third-party timed mock ≥ 80–85% Aim above pass threshold as safety margin, not guarantee
Domain floor ≥ 75% per domain No severe weak domain masked by a strong one
Architecture ADR drills Explain chosen service + two rejected alternatives Reason from requirements

Exam traps and design warnings

  • A 700 pass mark is a scaled score, not necessarily 70% raw accuracy.

  • Repeatedly memorizing the same practice-bank items inflates measured readiness.

  • Old service names or retired SKUs may be best exam-era answers but poor new-deployment recommendations.

Guided lab: Final architecture board

  1. Complete one closed-book, timed, mixed-domain mock and record only first-attempt answers.

  2. Re-read the Litware facts, answer 12 cards blind, and justify each as a 90-second architecture recommendation.

  3. Create a one-page “decision matrix” of 20 commonly confused Azure services.

  4. Re-check current official objectives and the change log before booking your exam.

Evidence to retain: one diagram, one option-comparison table, a short ADR, a verification screenshot/command result (where actually implemented), and a teardown/cost note.

Tie-in to your question bank

  • One fresh set of 60 mixed practice items; do not use disputed questions in scoring.

  • Revisit all items marked incorrect at 1-day, 3-day and 7-day intervals.

  • Use the official Microsoft practice assessment and at least one independent timed mock.

Practice schedule: learn without memorising bad answers

First attempt: Hide the answer and score only questions with sufficiently complete source evidence. Second step: explain which word in the requirement eliminates each alternative. Third step: compare against Microsoft docs, then only mark as validated if the source and your explanation agree. Spaced reviews: attempt again after 1, 3 and 7 days. Red flags: missing tab, obscured table, missing answer choice, outdated product or contradictory constraints. Such items are learning prompts, not scored evidence.

Worked architect case study | Litware

The uploaded Litware screenshots are a separate 12-question case study, not bank questions 1–12. Relevant themes: immutable Blob data, SQL Managed Instance and zone availability, RBAC, hierarchical namespace for data lake, reservation cost management, Azure Policy remediation, private endpoints and Conditional Access. The prior review identifies duplicate question pairs and a conflict between a two-zone outage assertion and an unconditional SQL availability guarantee. Use these as architecture decision exercises, not blindly as fact.

Exercise: Draw an application landing zone with a private data tier, central policies, hybrid connectivity, backup/restore paths and a regional recovery design. State the source requirements. Challenge ambiguous resilience claims; define the explicit recovery target and validate the SKU/region capabilities before recommending Business Critical or a failover group.

2026 technology change watch
  1. Azure Cache for Redis: Microsoft is moving customers to Azure Managed Redis; retirement and new-creation restrictions depend on tier and customer status. Check the current FAQ before choosing a Redis SKU for new deployments.
  2. Azure Cosmos DB for PostgreSQL: New deployments are blocked on its retirement path; the recommended successor for distributed PostgreSQL is Azure Database for PostgreSQL Elastic Clusters. Retain historic exam context but distinguish it from a production recommendation.
  3. App Service backup: Automatic versus custom backup frequency, portability and supported plans need to be checked against current service limits.
  4. Question-bank screenshots: If a question is incomplete or internally contradictory, label it not gradable until evidence is available.
  5. 2026 exam blueprint: Validate exam objective changes near exam day; video courses recorded earlier may cover legacy SKU choices.

Extended hands-on labs: safe execution and evidence

These are optional applied exercises. If you cannot use a paid subscription, do the design, CLI query and ADR steps without deploying paid resources. When deployment is appropriate, first set a budget or use a disposable lab subscription, record the resource names, and tear down at the end. Do not deploy in a production tenant.

Lab A - Resource inventory, hierarchy and policy

Scenario: a company requires regional data control and mandatory cost tags. Produce a policy initiative proposal, assigned at a management-group scope, with evidence for exemptions and remediation.

  1. Inspect the tenant, subscription and visible policy assignments using read-only Azure CLI commands.
  2. Design the management-group tree and two policies: allowed locations and inherit/copy a required cost-center tag.
  3. State whether each policy should Audit, Deny, Modify or DeployIfNotExists; justify assignment identity and RBAC.
  4. Write a test matrix covering compliant resources, untagged resources, exempt groups and rollback.
  5. Create a documented decision, not a live tenant-wide production policy.
az account show --output table
az account list --output table
az policy assignment list --output table
# Read-only examples; sign in only to a tenant you control.

Lab B - Private connectivity and diagnosis

Scenario: an app in a spoke VNet must access a storage account privately, while corporate clients resolve the same private endpoint over hybrid connectivity.

  1. Document VNet and subnet CIDRs, hub firewall, gateway, resolver forwarding and the storage private endpoint.
  2. Identify the public FQDN, private DNS zone and how the client reaches the private IP.
  3. Trace the request from corporate DNS to Azure private resolver, then to the private endpoint.
  4. Compare the solution with service endpoints; address exfiltration, firewall and routing risks.
  5. Validate expected DNS and network paths before disabling public network access.
az network vnet list --output table
az network private-endpoint list --output table
# Inspect effective routes / NSG rules in a test environment.

Lab C - Monitoring service selection

Scenario: operations require immediate production error detection, 90-day searchable logs, a five-year archive and a third-party SIEM.

  1. Identify platform metrics, resource logs, Activity Log events and application telemetry separately.
  2. Design diagnostic settings to Log Analytics, Event Hubs and Storage; check supported categories.
  3. Estimate daily GB ingestion, retention and SIEM egress costs.
  4. Draft KQL investigations for failed authorizations and request latency above an SLO.
  5. Produce a monitoring RACI and response runbook with false-positive control.

Lab D - SQL architecture and recovery validation

Scenario: the source app has cross-database queries, unpredictable traffic and an RTO of one hour. The recovery site must withstand a regional failure.

  1. Compare SQL Database, elastic pools, Managed Instance and SQL on VMs against feature compatibility.
  2. Specify service tier, zone strategy and cross-region failover approach, including replication lag.
  3. Calculate the acceptable loss from the business RPO and have stakeholders sign off.
  4. Plan PITR/backup and ransomware response separately from replica availability.
  5. Test restore/failover in a disposable environment and record actual RTO/RPO.

Lab E - Principal architect design-review presentation

Deliver an eight-minute review: context (1 min) → requirements (1 min) → diagram (2 min) → alternatives and cost (2 min) → failure and security risks (1 min) → test and rollback (1 min). Challenge your own design with changed constraints: twice the load, half the budget, one unavailable region, mandatory private endpoints or a security incident.

Sample worked scenario - selecting a minimal enterprise design

Business requirements: a regional sales API must serve 200 requests/s, keep PII on private connectivity, retain audit events for one year, integrate with a legacy on-premises SQL component and restore from a regional failure within four hours.

Area Initial shortlist Required evidence
Entry Application Gateway with WAF vs Front Door Regional versus global requirement, TLS and WAF boundary
Compute App Service vs Container Apps vs AKS Runtime, scale-out and ops burden
Data SQL Managed Instance vs SQL Database Cross-database compatibility and migration test
Hybrid VPN Gateway vs ExpressRoute Bandwidth, redundancy, encryption and cost
Private PaaS Private Endpoints plus private DNS Name resolution from all consuming networks
Operations Monitor, App Insights and Log Analytics APM, platform metrics and audit retention
Recovery SQL regional DR plus tested restores Demonstrate RTO/RPO, restore and failover plan

Possible architecture: a regional Application Gateway → App Service API → SQL Managed Instance, with Private Endpoints, private DNS, hybrid connectivity, monitoring and cross-region recovery. This is not uniquely correct: choose Front Door for global entry, Container Apps for container-first applications, or an alternative database if requirements permit. Validate support by SKU/region before approval.

Review questions: What if the on-premises dependency is offline? What is the data-loss budget? Can every consumer resolve private DNS? Are cross-database transactions actually required? What is the standby cost? Who can delete backups?
